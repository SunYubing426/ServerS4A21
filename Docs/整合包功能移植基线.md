# S4A21 整合包功能移植基线

> 文档用途：记录 `S4A21-整合包（含GM及登陆器）` 向当前 `ServerS4A21` 主线移植前的事实基线、边界和验收规则。
>
> 当前状态：M0（移植基线）、M1（玩家交易）与 M2（黑钻售货机）源码移植已完成；Windows .NET 10 编译、自测和客户端实机验证待执行。

## 1. 主线和参考树

- 当前主线：`ServerS4A21-mine`。
- 参考树：同级目录 `S4A21-整合包（含GM及登陆器）`，默认只读。
- 参考树不是 Git 仓库，不能使用提交历史判断修复来源；功能差异以源码、协议注册、数据库迁移和 SelfTest 为证据。
- 禁止直接覆盖当前 `Server/DfoServer`、`SqliteMigrations.cs`、`item_schema.sql` 或 `PacketTypesA21.cs`。

## 3. 当前主线必须保留的能力

以下内容以当前主线为准，整合包代码不得覆盖：

- Licensed Dungeon、镜像阿拉德、时空裂缝和每日入场限制。
- 当前 Dungeon/Quest/Settlement 的 generation、timer、恢复和幂等边界。
- 当前 Inventory 的 `InventoryContext -> InventoryLease -> InventoryService` 在线真源。
- 当前 SQLite 基线和迁移校验。
- 当前更完整的 SelfTest 集合，包括 PC 房时点、DungeonExperience、执照副本等。
- 当前已验证的掉落、经验药水、SP 点数书、支援兵资格和 QuestAssistant 规则。
- 当前协议枚举文件 `Network/Core/PacketTypesA21.cs` 的命名和数值。

整合包中更宽松的行为（免注册自动建号、同账号多开、较宽松的觉醒门槛等）属于运营策略，不视为自动修复。

## 4. 数据库合并规则

### 4.1 基线

- 当前主线基线：`86jp-database-v1`。
- 当前主线迁移链最后版本：`schema v26`，其中 v13-v26 已被当前副本、活动、疲劳和执照功能使用。
- 整合包迁移链虽然到 v36，但 v16-v36 的版本含义与当前主线不同，禁止直接复制或复用版本号。

### 4.2 新模块迁移

所有新迁移从当前主线最新版本之后连续追加。实际版本号以开始实现时数据库状态为准，不提前占号。每个迁移必须同时修改：

1. `Server/DfoServer/Sqlite/item_schema.sql`；
2. `Server/DfoServer/Sqlite/SqliteMigrations.cs`；
3. 对应数据库 SelfTest；
4. 相关业务文档。

新库必须一次创建出完整结构；旧库必须逐级升级。禁止运行时隐式建表、恢复整合包旧种子库或把整合包数据库直接复制到当前主线。

### 4.3 每次迁移的最低验证

- 新库创建并标记正确 baseline/version。
- 当前最新库升级到新版本。
- 重复执行迁移保持幂等。
- 迁移中途失败后事务回滚。
- 错误 baseline 或跳跃版本拒绝启动。
- 升级库重启后可以正常读取和继续保存。
- `item_schema.sql` 新库与逐级升级库的表结构一致。

## 5. 协议接入边界

- A21 CMD/NOTI 名称和数值只从当前主线 `PacketTypesA21.cs` 获取。
- 整合包中的裸数字只能作为线索，不能直接复制到业务代码。
- 每个新命令必须确认 body 长度、字段顺序、端序、ACK/NOTI 顺序、重复请求和失败回包。
- 协议处理器只做解析、权限前置和编排；业务规则放在 `Game/*` 服务；持久化走 Repository/CommitService/Coordinator。
- 没有当前客户端抓包、逆向、PVF 或已验证 SelfTest 证据的字段标记为“待确认”，不得以占位布局宣称完成。

## 6. Inventory 合并硬规则

所有会改变在线物品、金币、材料、宠物、时装或仓库的模块必须：

- 获取当前 session-owned `InventoryLease`；
- 在 `lease.SyncRoot` 内读取、校验和修改；
- 使用现有 `InventoryRewardGrantService`、`InventoryDeleteService`、`InventoryMoveService` 或对应 CommitService；
- 多方变化使用统一 SQLite 事务；
- 事务提交成功后才能发送成功 ACK/奖励通知/刷新包；
- 失败恢复在线内存快照，禁止退回独立连接直接写库；
- 不使用整合包 `GmStyleItemGrant` 作为在线业务路径。

## 7. M1 玩家交易的预定边界

第一批只处理玩家交易，不同时合并售货机、活动或公会。

目标链路：

~~~text
Parser
  -> Party/Trade Handler
  -> PlayerTradeCoordinator
  -> 双方 session/generation/ticket 校验
  -> 按角色 ID 顺序锁定双方 InventoryLease
  -> 克隆背包试算
  -> 双方同事务 SaveDirtyPair
  -> 提交后发送交易结果和物品刷新
~~~

必须覆盖：普通物品、金币、堆叠物品、虚拟材料、绑定/过期物品、重复报价、报价后物品变化、背包容量不足、双方同时确认、取消、断线、持久化失败回滚和旧 ticket 回调失效。

## 8. M2 黑钻售货机实现边界

当前实现覆盖：

- 从 PVF `etc/vendingmachine.lst` 及 `pcroom.vm`/`pcroom4.vm` 读取机器、材料和权重奖励池；
- 仅允许 A21 售货机 `1/3`、组 `1`，请求体固定 10 字节并拒绝非法槽位；
- 使用当前 session-owned `InventoryLease`，在同一 SQLite 事务中校验黑钻 type `12`、扣除材料、发放普通或 Premium 奖励；
- 背包不足时经事务绑定的 Mailbox overflow sink 投递，提交成功后才发送 ACK、库存刷新、邮箱提示和 Premium 通知；
- 选角和 USERINFO subtype0 投影刷新黑钻标志，并在进号后补发有效黑钻状态通知。

聚焦自测命令为 `--selftest-vending-machine`；该测试依赖可用的 `PVF_ARCHIVE_PATH`，并覆盖协议边界、权重边界、材料/资格校验、背包溢出、邮件失败、Premium 激活、持久化失败回滚和旧 lease 拒绝。

## 9. M0 基线验证记录

本机只完成只读检查，未修改业务代码：

- 当前工作区：`master`，开始时无未提交修改。
- 当前主线有效 C# 文件约 1082 个；参考树排除 `bin/obj` 后约 1147 个。
- 参考树比当前主线多出约 68 个有效 C# 文件，主要集中在账号、公会、拍卖、活动、交易和售货机。
- 当前主线保留参考树没有的 `A21PcRoomTimePointEventSelfTest.cs`、`DungeonExperienceSelfTest.cs` 等测试/功能文件。
- 当前 Mac 只有 .NET SDK 8.0.416；项目目标为 .NET 10，执行构建得到 `NETSDK1045`，因此本机没有进行源码构建验收。
- Windows 继续时必须使用 .NET 10 SDK 重新执行构建和 SelfTest，不能使用旧 `bin/obj` 产物代替。

## 10. Windows 续作入口

恢复 Codex 会话后，先执行：

~~~powershell
git status --short --branch
dotnet --version
dotnet build Server/DfoServer/DfoServer.csproj -c Debug --nologo
~~~

确认 Windows 构建通过后，依次执行 M1/M2 聚焦自测，再开始 M3.1：

1. 阅读本文件第 7、8 节和 `Docs/新版背包架构业务接入规范.md`；
2. 串行执行 `--selftest-player-trade`、`--selftest-vending-machine` 和 `--selftest-all`；
3. 使用当前 PVF 与双客户端完成交易、黑钻资格、奖励溢出和重登验证；
4. 验证通过后再进入 M3.1 活动公共框架。
